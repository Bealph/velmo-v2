#             -o requirements.txt
#
# POURQUOI CE FICHIER EXISTE
#
# Le moteur de build d'Azure App Service (Oryx) applique la premiere regle qui
# correspond a la racine du depot : `requirements.txt` d'abord, sinon `pyproject.toml`
# + `uv.lock` via uv. La voie uv semblait suffire — c'est le gestionnaire du projet —
# mais elle ne l'est pas : streamlit et le client OpenAI ne sont pas des dependances
# principales, ils vivent dans les extras `demo` et `llm` (voir le Makefile, qui lance
# `uv run --extra llm --extra demo`). Un `uv sync` nu ne les installe pas.
#
# L'application ne demarrerait donc pas, et l'agent retomberait silencieusement sur son
# repli hors-ligne EchoLLM : une demonstration qui n'appelle jamais le modele.
#
# Ce fichier leve l'incertitude sur la commande exacte qu'Oryx execute, sans toucher a
# la structure des extras, utile en local. Il est engendre depuis `uv.lock` : aucune
# divergence de versions possible. L'extra `vector` en est volontairement absent —
# PyTorch (~2,5 Go) ne tient pas sur un plan B1 (1,75 Go de RAM), et la FAQ retombe sur
# la recherche lexicale locale, ce que le dossier de deploiement a acte.
#
# La premiere ligne, `-e .`, n'est pas decorative : le paquet doit etre installe DANS
# l'arborescence du depot. `kb_store.py` resout `kb/docs` en remontant depuis son propre
# fichier ; installe en roue dans site-packages, il ne trouverait plus la FAQ — et aucune
# erreur ne serait levee.
#    uv export --format requirements-txt --no-dev --no-hashes --extra llm --extra demo
